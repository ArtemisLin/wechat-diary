# 参赛说明 | Eazo「Personal Agent」挑战

> 本文件为赛事材料: 作品定位、AI 能力说明、体验与评测指引。
> 产品本体的一切以 [README](../README.md) 与 [数据契约](data-contract.md) 为准。

## 一、这个 Agent 为谁而做

需求起点是作者本人: 一个白天对人高强度输出、晚上需要倾倒的人。多年想坚持记
日记, 每次都死在同一个地方——打开 App、登录、面对空白编辑框的那点摩擦, 在深夜
刚好足以让人放弃。

真实需要只有一句话: **累了一天之后, 能对着微信说几句话, 它就成为我自己的日记,
存在我自己的电脑里。**

现有产品为什么不满足:
- 日记 App: 数据在别人服务器上, 格式是私有的, App 停运日记就成了人质
- 备忘录/微信文件传输助手: 记完就沉底, 不成库、不成契约, 没有提醒
- 通用 AI 助手: 什么都能聊, 但你的话去了哪里、明天还找不找得到, 没有承诺

wechat-diary 的回答是做一条"刚好够用"的管道: 微信是输入 (最高频的入口, 配合
语音输入法说话即打字), 本机纯 markdown 是归宿 (数据主权), 每晚 22:00/23:00
是它唯一主动的时刻 (未写提醒)。它**刻意不做**回顾、分析、情绪评分——管理这个库
是用户和用户自选 Agent 的自由, 本项目通过只读 MCP 接口把这份自由交出去。

赛道原话说: "复杂不等于有价值。一个只解决很小的问题, 却确实被某个人反复使用的
Agent, 同样可能成为优秀作品。"——这个项目就是按这句话的标准做的: 作者本人日用,
真实日记库已连续积累数月。

## 二、AI 在核心体验的哪里

这不是一个聊天 Agent。LLM 在两个位置参与核心体验, 每一处都克制且必要:

1. **口语 → 日记的整理** (核心链路): 深夜的语音倾倒经微信转写后是口语碎片——
   断句混乱、语气词密集、一句话绕三圈。LLM 负责轻度润色整形: 去语气词、理顺
   断句、适当分段, **禁止改写语义、禁止加入用户没说的内容** (原话即史料, 见
   diary_writer.py 的 POLISH_PROMPT)。转写噪音千人千面, 规则引擎不可枚举,
   这是 LLM 的活。
2. **闲聊模式的守门** (防误记设计的一半): 不在记录模式时说的话不会被记, 由一个
   带严格 system prompt 的 LLM 接住——≤50 字、不评判、不说教、不冒充模式切换,
   在用户明显讲述今天的事时柔和引导「发『开始记日记』就开始」。它的职责不是
   聊天, 是守住"哪些话进日记"的边界。

(意图识别刻意**不用** LLM: 短命令走规则引擎, <1ms、零成本、可解释——在哪里用
AI 和在哪里不用, 是同一个设计判断。)

刻意的负面清单: LLM 永不决定写什么进日记 (落盘原样)、永不主动发起对话、
永不生成"洞察"或建议。**AI 失败时原文照存, 用户的话永不丢失**——"零 key 可用"
是可靠性兜底, 不是 AI 缺位: 推荐配置下 LLM 全程在链路里。

## 三、体验方式 (三选一, 由浅入深)

1. **下载单文件版直接体验** (最快, 约 2 分钟): 从仓库 Releases 下载
   `wechat-diary-windows.exe` (免解压免安装, 另有 macOS 版), 双击 → 浏览器
   自动打开本地向导 → 用自己的微信扫码 → 点选一个文件夹 → 启动。之后在微信里
   给 bot 发「开始记日记」, 说几句话, 发「结束」——完整走一遍记录闭环, 日记
   就落在刚选的文件夹里。不需要 Python、不需要配置文件、不需要任何 AI key。
   (没有"加作者的 demo bot"这条路是有意的: 本产品单用户、数据不过任何第三方
   服务器, 每个体验者的管道都完整跑在自己机器上——下载即体验正是产品形态本身。)
2. **5 分钟源码部署**: 见 README「5 分钟源码部署」, clone → 装依赖 →
   扫码 → 启动。
3. **MCP + 演示库** (给 AI 客户端/评测机): 见下节。

## 四、技术评测指引 (动态/静态测评)

**MCP 接口 (技术连通性验证入口)**:

```bash
# 零依赖, Python 3.9+ 标准库即可运行; 接演示库 (仓库自带, 合成数据):
DIARY_DIR=docs/demo-vault python src/mcp_server.py

# Claude Code 一行接入:
claude mcp add wechat-diary -- python /abs/path/wechat-diary/src/mcp_server.py
```

- stdio 传输, JSON-RPC 2.0, 实现 initialize / tools/list / tools/call / ping
- 工具全部只读: `diary_read(date)` / `diary_search(query, limit, date_from,
  date_to)` / `diary_recent(n)`; 写入在架构上只有微信管道一条路 (mcp_server.py
  不 import 任何写入模块)
- 演示库 `docs/demo-vault/` 为标注明确的合成数据, 严格遵守数据契约

**测试与工程质量**:

```bash
python -m pytest tests/ -v   # 251 个用例; CI 于 Python 3.11/3.13 双矩阵运行
```

- 数据契约文档化 ([data-contract.md](data-contract.md)): 只追加、原子写入、
  时区强制北京时间
- 可靠性: 崩溃自动重启、session 过期自动重登、错过提醒启动补偿、离线消息
  按 cursor 补拉
- 诚实的限制在 README 显著位置声明 (电脑关机管道即停; iLink 平台约 20 小时
  无互动不能主动发消息)

## 六、赛道六问

1. **从谁开始?** 作者本人——一个多次尝试记日记均告失败、但每天都在微信里说话
   的人。
2. **什么场景什么问题?** 深夜倾倒欲最强、意志力最弱; 任何"打开 App 面对空白
   页"的摩擦都足以杀死记录。
3. **为何现有产品不满足?** 日记 App 要求数据托管与新习惯; 备忘录不成库无契约;
   通用助手对"你的话归你"没有承诺。
4. **Agent 如何进入真实生活?** 寄生在已有习惯里: 微信说话。产品没有要求用户
   学任何新东西——命令一共三个词。
5. **用后发生了什么?** 作者从"从未坚持超过一周"到连续记录数月; 断记时 22:00
   的提醒把人拉回来。(复赛前补充: 至少一位同画像用户的两周试用与反馈迭代)
6. **相似用户是谁?** 晚间复盘型职业者——咨询师、自由职业者、独立开发者: 白天
   对人输出、晚上需要不评判的出口、坚持数据攥在自己手里的纯文本用户。
